一、专项一：向量嵌入系统（UI/风格/模板）深度定位 + 问题卡点根治指导

1. 核心业务定位（为什么是平台命脉）

你这套AI一键出全套UI的核心不靠大模型瞎猜，靠向量精准匹配：把UI组件、配色方案、字体版式、页面模板、行业UX规则全部转成固定维度向量入库；用户输入自然语言需求，先做向量相似度检索，再让AI基于检索结果拼装完整项目框架，直接决定生成准确度、UI还原度、推理速度三大核心指标，是全平台底层核心命脉。

2. 强制技术收口（严格贴合前文数据库选型）

✅ 禁止单独部署自研向量引擎/第三方独立向量库
✅ 统一收口：PostgreSQL + pgvector 原生一体化承载
✅ 向量固定维度：全文UI资源统一标准化维度，不混维、不异构
3. 落地高频致命卡点精准定位（提前规避）
- 卡点1：多来源向量维度不统一：shadcn组件、主题配色、模板页面向量维度混乱，直接导致匹配错乱、UI风格跑偏、生成半成品框架。
- 卡点2：向量只存不建分层索引：海量UI资源入库后未分区、未建向量专项索引，并发用户提问时检索延迟暴涨，平台卡顿超时，AI响应直接卡死。
- 卡点3：嵌入模型与业务不匹配：通用文本嵌入模型硬套UI视觉资源，语义和视觉特征脱节，出现“需求要电商后台，向量匹配出社交首页”的低级错配问题。
- 卡点4：冷热数据混堆存储：热门行业模板、高频UI组件和老旧废弃素材混存，挤占核心数据库算力，拖慢全平台AI生成链路。

4. 专项根治落地指导（一步到位适配现有库）

① 四层向量分类结构化入库（对齐三大资源库）
- 第一层向量：UI原子组件向量（绑定shadcn/ui全量组件）
- 第二层向量：视觉风格向量（57+UI风格、96+行业配色、57+字体全套绑定）
- 第三层向量：UX交互规则向量（对接99条最佳实践、100条行业专属规则）
- 第四层向量：完整页面/项目模板向量（电商、SaaS、管理后台全品类预制）
② 强制索引+分区优化（贴合PostgreSQL底层）
按行业、使用热度、UI场景做物理分区；给四类向量统一创建余弦相似度专项索引，毫秒级召回，扛住高并发AI会话请求。
③ 向量闭环联动业务逻辑
用户输入需求 → 向量库Top-N精准召回匹配资源 → 送入大模型定向拼装框架 → 输出合规UI+完整工程 → 自动回写新生成组件向量，完成自迭代闭环。

二、专项二：MCP模型上下文协议全链路对接（AI+Figma+数据库+前端四方打通）定位指导

1. 核心业务定位（平台联动中枢）

MCP不是简单通信接口，是全平台统一上下文调度总线：负责打通AI大模型、Figma官方源文件接口、Next前端工程、PostgreSQL核心数据库四方实时互通；没有标准MCP对接，AI只能孤立生成文本代码，无法自动调取资源库、无法回写项目数据、无法联动Figma双向同步，直接断了一键生成全套UI的核心链路。
2. 强制对接收口（贴合原有技术栈不扩配）

✅ 轻量化封装MCP标准，不引入重型中间件
✅ 对接链路固定：大模型会话层 → MCP总线 → 前端资源网关 → 数据库读写接口 → Figma文件同步接口
✅ 权限复用：直接沿用PostgreSQL行级原有权限体系，不用二次搭建权限架构

3. 高频对接失败卡点精准定位
- 卡点1：上下文断层割裂：AI只接收用户单句需求，MCP未同步推送用户所属团队、项目类型、历史设计偏好、权限标签，生成UI和用户实际业务场景完全脱节。
- 卡点2：Figma源文件只读不入库：MCP只拉取Figma预览数据，未同步写入MongoDB素材库+PostgreSQL项目台账，无法版本回溯、无法二次编辑复用。
- 卡点3：AI生成结果单向流出：MCP只负责下发指令，不负责回写生成日志、组件使用记录、模板调用台账，无法做数据沉淀和平台迭代优化。
- 卡点4：会话无状态雪崩风险：高并发场景下MCP未联动Redis缓存会话上下文，重复请求、无效请求挤占带宽，高峰期平台直接雪崩卡顿。
4. MCP专项落地对接标准（直接抄配上线）

① 三段式标准报文结构（强制统一格式）
Header：用户ID、项目ID、团队权限、设备环境、资源访问标签
Context：向量检索ID集合、匹配组件ID、风格主题ID、预置模板编号
Payload：用户原始自然语言需求、Figma文件快照地址、工程输出路径
② 双向双向同步绑定
上行：AI主动读取向量库、读取模板库、校验UX规则权限
下行：生成结果自动写入项目表、写入版本快照、写入组件调用统计台账
③ 熔断+降级兜底机制（商用必备）
MCP链路超时自动熔断，切回本地预制模板兜底；异常流量自动限流，保护核心数据库不被击穿，保障平台稳定运行。

三、专项三：全量资源增量同步机制（组件/模板/Figma资产/向量）专项定位指导

1. 核心业务定位（平台长效运维核心）

增量同步决定平台能不能长期低成本运营：不用全量重建数据库、不用全量重算向量、不用停机维护；只同步新增UI组件、新增行业配色、新增业务模板、新增用户生成资产；保障平台资源持续更新、AI越用越准、数据库负载始终平稳，不影响线上用户正常使用。

2. 增量同步分层收口（贴合四类数据库分工）
✅ PostgreSQL：增量同步结构化项目数据、权限数据、规则配置数据
✅ pgvector联动：增量追加新组件/新风格向量，存量向量不重复计算
✅ MongoDB：增量同步Figma快照、UI大图、历史版本素材
✅ Redis：增量刷新热门模板缓存、活跃用户会话上下文

3. 同步翻车核心卡点精准定位（必防）

- 卡点1：全量重刷向量，算力爆炸：每次更新组件都全量重新计算全库向量，CPU内存拉满，线上AI服务直接中断瘫痪。
- 卡点2：同步时序错乱，数据脏写：UI素材、模板数据、向量索引三方写入时序不一致，出现有组件无向量、有向量无样式的脏数据，AI匹配直接失效。
- 卡点3：多环境同步冲突：开发、测试、生产环境资源混同步，劣质测试组件流入生产资源库，线上UI生成批量翻车。
- 卡点4：无版本回滚点：增量同步出错后无快照兜底，无法一键回退，只能删库重跑，直接中断平台商用服务。

4. 增量同步落地标准流程（零停机、零脏数据）

① 先校验 → 后入库 → 最后增量算向量
第一步：校验新增UI组件/模板合规性，核验是否符合UX底层规则
第二步：增量写入业务主库与素材库；
第三步：仅对新增资源单独计算向量，存量数据不动；第四步：异步轻量刷新局部向量索引，不占用核心算力。

② 时间戳+水印双锁机制
所有同步数据带唯一增量水印+时间戳，避免重复写入、跨机重复同步，彻底杜绝数据冗余脏数据。

③ 影子库灰度同步切换
先同步至影子备用资源库，灰度抽检UI匹配效果、生成准确度，无异常后再无缝切线上主库，全程用户无感知、零停机。
